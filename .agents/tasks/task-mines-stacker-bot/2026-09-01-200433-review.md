# MINES STACKER BOT — mobile-only Mines analysis/visualisation app

A self-contained static HTML/CSS/JS app (no framework, no build, no network) implementing the required flow: enter or generate a seed, pick a mine count (1–24), tap Analyze, watch a ~2.2s evaluation animation, then read an auto-generated 5×5 grid of exactly 25 fully-revealed cells. A seeded PRNG (xmur3 → mulberry32) drives a Fisher-Yates shuffle to deterministically pick 4–5 safe gem tiles; every other cell renders as a gray "mines gradient" and true bomb positions are never exposed. The logo is wired through `assets/logo.png` with an `onerror` fallback to a neutral placeholder SVG, so the real gorilla art drops in later with no code changes, and no gorilla was drawn.

Watch for: the selected mine count is pure display context — it never influences the grid, so the number of gray tiles is identical whether the user picks 1 mine or 24 (confirmed); this is consistent with the spec's "just show 4–5 safe tiles, keep others gray" wording but is worth a conscious sign-off. `maximum-scale=1` disables user zoom, an accessibility trade-off (confirmed).

**Verdict**: APPROVED

## High-level view

The generation model is deterministic and correctly scoped: xmur3 hashes `seed + "::" + mines`, mulberry32 produces the stream, and a Fisher-Yates shuffle selects the gem indices. I confirmed by replicating the exact algorithm in Node that the grid is always 25 cells, always 4–5 gems, reproducible for the same seed+mines, and different when either input changes. Bomb positions are never computed or rendered, so there is no path by which a mine location can leak — the `.cell.mine` red style exists in CSS to satisfy the spec's "define the state" requirement but is intentionally never applied.

The mine count is folded into the PRNG seed (so changing it changes the layout) but is never used to place bombs or size the gray region. That means "Mines: 24" and "Mines: 1" both yield 20–21 gray tiles. This faithfully follows the literal instruction, but it is the one place where a reader might expect the selection to mean something and it does not.

The app is genuinely offline and dependency-free: the only URL anywhere is the SVG XML namespace in the placeholder logo, which is not a network fetch. Cells carry no click, reveal, or selection handlers, so it is a visualisation surface and not a playable game. The stage machine guards Analyze until both a seed and a mine count exist, Re-analyze reproduces the same grid, and Reset returns to the seed stage.

The logo strategy is sound: `object-fit: contain` plus `max-width` on a fixed-size wrapper means a real high-res `logo.png` renders undistorted, and the `onerror` fallback keeps the layout intact until it is added. No artwork was recreated.

<summary>Details</summary>

### Deterministic generation and the reveal rule

`makeRng` hashes `String(seed) + "::" + String(mines)` through xmur3, seeds mulberry32 with the first output, and hands back the stream. `buildGridModel` draws `gemCount = 4 + floor(rng()*2)` (4 or 5), then Fisher-Yates shuffles `[0..24]` and marks the first `gemCount` indices as gems. Replicating the exact algorithm outside the browser over 20,000 seed/mine combinations produced only gem counts of 4 or 5 (≈50/50 split), always 25 cells, identical output for repeated same-input calls, and divergent output when either the seed or the mine count changed. Because gems are the only positive state written and gray is the default, there is no code path that can render a bomb — the reveal-rule guarantee is structural, not incidental. The `.cell.mine` red-bomb style is defined in CSS but never attached by the renderer, which is exactly what FEAT-001 asked for.

### Mine count is display-only

`state.mines` feeds two things: the PRNG seed string and the "Mines: N" label. It never sizes the gray region or the gem set. A user selecting 24 mines and a user selecting 1 mine both see 20–21 gray tiles; only the specific layout differs because the seed string differs. This is a faithful reading of the instruction ("don't show all the mines or where bombs are, just show 4–5 safe tiles and keep others gray"), so it is not a defect — but it is the single most likely spot for a reviewer or future maintainer to assume the selector drives the visualisation when it does not. Worth an explicit sign-off.

### Mobile-only styling and the zoom trade-off

The viewport meta is present and the layout is constrained to a 430px `max-width` centered container with a dark neon/gradient theme. One caveat: `maximum-scale=1` disables pinch-zoom, which some users rely on. It is a common choice for "app-like" feel but is an accessibility trade-off; dropping it costs nothing visually unless locked zoom is intentional.
